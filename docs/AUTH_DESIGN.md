# 외부 서버 없는 인증 설계

작성일: 2026-11-06

## 결정

GitHub Pages + Firebase Authentication + Firestore만 사용한다. Firebase Functions, Cloudflare Workers, 별도 API 서버를 배포하지 않는다. Firebase Spark의 제공 한도 내에서 개발·운영할 수 있도록 기존 클라이언트 인증 구조로 정리한다. 무료 사용 한도는 각 서비스 정책을 따른다.

사용자 선택은 **외부 서버 없이 가능한 범위**다. 기존 이메일 로그인·비밀번호 재설정, 이메일 비공개와 기존 계정·UID·게시물을 보존한다. 이 조건에서 핸들은 공개 프로필 식별자로 사용하고, 로그인 ID는 이메일로 명확하게 표시한다.

## 제공하는 흐름

1. 가입 1단계에서 실제 이메일과 비밀번호를 입력한다. 브라우저 자동완성은 이메일을 `username`, 비밀번호를 `new-password`로 식별한다.
2. 가입 2단계에서 고유 핸들과 닉네임을 필수 입력한다. Firebase Auth 계정 생성과 기존 Firestore 프로필 트랜잭션으로 가입을 완료한다.
3. 로그인은 `signInWithEmailAndPassword`로 Firebase Auth에 직접 요청한다. 핸들 입력을 이메일로 변환하는 API나 공개 DB 조회는 하지 않는다.
4. 비밀번호 재설정은 기존 실제 이메일로 Firebase Auth가 발송한다.
5. 핸들은 프로필 주소, 작성자·반응자 표시, `@핸들` 검색에 사용한다. 핸들 변경은 최근 14일 두 번이라는 기존 규칙을 유지한다.

이름·핸들·소개·SNS는 기존 공개 프로필 정책을 유지한다. 실제 이메일과 비밀번호는 공개 `profiles`·`handles` 문서에 저장하지 않는다. 이메일은 Firebase Auth가 관리하며 비밀번호는 Firebase SDK에만 전달한다. 이메일별 핸들 로그인용 매핑을 브라우저 저장소에 새로 저장하지도 않는다.

## 핸들 로그인 범위

아이디 로그인이 본질적으로 유료여서 제외하는 것이 아니다. Firebase Auth의 현재 사용 중인 이메일·비밀번호 API는 로그인에 실제 이메일을 요구한다. 기존 계정의 이메일을 익명 방문자가 알 수 없게 하면서 핸들로 변환하는 서버도 두지 않기로 했으므로, **이번 설계에서는 전역 핸들 로그인을 지원하지 않는다**. UI에 지원한다고 표시하거나 동작하지 않는 서버를 호출하지 않는다.

다음 대안은 채택하지 않는다.

| 대안 | 채택하지 않는 이유 |
| --- | --- |
| 핸들 → 실제 이메일 공개 매핑 | 프로필 핸들을 아는 사람이 이메일을 수집할 수 있음 |
| 핸들에서 가상 이메일 생성 | 기존 실제 이메일 계정·비밀번호 재설정과 호환되지 않으며 핸들 변경에도 별도 이행이 필요함 |
| 브라우저에 핸들·이메일 연결 기억 | 다른 기기에서는 동작하지 않고 공용 기기에 이메일이 남음. 전역 핸들 로그인으로 표현할 수 없음 |
| 무료 호스팅의 인증 API | 과금 여부와 별개로 외부 서버를 추가하지 않는다는 사용자 선택에 맞지 않음 |

향후 핸들 로그인 자체를 다시 필수로 선택하면 인증 제공자를 바꾸거나 별도 비공개 조회 경로를 허용하는 요구사항 결정부터 다시 해야 한다. 현재 이메일 기반 계정을 암묵적으로 가상 이메일 계정으로 변환하지 않는다.

## 제거하는 항목

- `functions/`의 추적 중인 서버 소스·패키지·테스트·배포 안내
- Firebase Functions SDK 연결 및 호출
- Functions 에뮬레이터, 런타임 설정, CI 설치·테스트 단계
- `AUTH_WEB_API_KEY` 서버 설정 및 Blaze 가입 요구
- ‘이메일 또는 핸들’ 로그인 안내

Firestore의 이전 `loginAttempts` 기록은 존재하더라도 클라이언트가 읽거나 수정하지 못하도록 유지한다. 실제 값이나 계정·게시물은 지우지 않는다. 무시된 로컬 설정·캐시 파일도 이번 변경에서 삭제하지 않는다.

## 운영 반영

새 인증 서비스나 키가 필요하지 않다. 기존 Firebase 웹 설정 네 개와 이메일/비밀번호 로그인 설정을 그대로 사용한다. 기존 프로필·활동 기능에 필요한 Firestore 규칙도 유지한다. 이번 변경은 규칙 설명 주석 외의 권한 변경이 없으므로 인증 재설계를 위해 별도 새 규칙을 배포할 필요는 없다.

과거에 `resolveHandleLogin`을 실제로 배포했다면 프런트엔드가 호출하지 않는다고 서버 리소스가 삭제되지는 않는다. 해당 경우에만 Firebase 콘솔에서 그 함수를 별도로 삭제할 수 있다. 이번 작업에서는 운영 리소스 삭제나 요금제 변경을 수행하지 않는다.

## 검증 기준

- Functions 없이 Auth·Firestore 에뮬레이터만으로 두 단계 가입, 이메일 로그인, 글 작성·반응·프로필·테마 흐름이 완료된다.
- 핸들을 로그인 이메일 칸에 입력하면 이메일 입력 오류로 안내하며 비공개 이메일을 조회하지 않는다.
- 이메일 로그인·가입 폼에 자동완성 속성이 유지된다.
- 코드·빌드·CI에 Firebase Functions 호출 및 서버 설치 단계가 남지 않는다.
- 기존 계정 UID와 공개 핸들 예약·변경 제한 규칙은 그대로 유지한다.

검증 결과: 입력·프로필 테스트 10개, Functions 없이 Auth·Firestore만 실행한 실제 Chromium 통합 시나리오 2개가 통과했다. 두 단계 가입·이메일 로그인·비밀번호 재설정 발송 안내, 게시·반응·활동·프로필 이동·테마 유지가 포함된다. TypeScript·프로덕션 빌드·Actions 정적 검사도 통과했다. 운영 메일 수신과 브라우저별 비밀번호 저장 제안은 실제 사용자 환경에서 별도 확인한다. 기존 단일 번들 크기 경고는 후속 성능 작업으로 남는다.
