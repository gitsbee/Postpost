## 1. 현재 상태와 검토 범위

사용자가 배포 사이트에서 로그인과 글 게시 성공을 확인했다. 기본 서비스 흐름이 완성된 상태이므로, 다음 단계는 **글을 잃지 않고 작성하고, 다시 찾아 읽고, 직접 관리할 수 있는 경험**을 만드는 것이다.

이 문서는 제공된 실제 화면과 저장소의 UI, Firebase 연결, Firestore 규칙, 테스트, 배포 워크플로를 검토해 작성했다. 운영 데이터나 콘솔 설정은 변경하지 않았으며, 아래 최초 제안의 관찰 내용은 개선 전 상태를 기록한 것이다. 이번 구현 범위와 완료 결과는 이 문서 앞뒤의 추가 섹션에서 확인할 수 있다. 화면에 대한 평가는 첨부된 데스크톱 화면 기준이다. 모바일 실기기, 색 대비 수치, 네트워크 지연과 운영 비용은 이번에 측정하지 않았다.

현재 유지할 장점:

- 크림색 배경과 녹색 계열, 카드 중심의 일관된 디자인
- 회원가입 → 로그인 → 텍스트 작성 → 실시간 목록으로 이어지는 간단한 흐름
- 비로그인 읽기, 로그인 후 작성이라는 이해하기 쉬운 권한 구조
- 작성자 UID, 본문 길이, 서버 시각을 검사하는 Firestore 규칙
- 환경 변수 누락 검사와 테스트·빌드를 포함한 Pages 배포 자동화

## 3. 먼저 개선할 사용자 경험

### 3.1 작성 중 글 보호 — P1

**관찰:** 본문은 `App.tsx`의 메모리에만 저장된다. 로고는 페이지 이동을 수행하고, 로그아웃 시에는 본문을 비운다. 새로고침이나 탭 종료로 초안이 사라질 수 있다.

**제안:**

- UID별로 초안을 분리해 자동 저장하고, 복원 시 저장 시각과 복원·폐기 선택지를 표시한다.
- 같은 탭 복원만 필요하면 `sessionStorage`, 브라우저 재시작 후 복원까지 필요하면 `localStorage`를 선택한다. 공용 기기에서 본문이 남는 차이를 고려한다.
- 로그아웃 시 저장·폐기 정책을 명시하고, 다음 계정에는 이전 계정의 초안을 노출하지 않는다.
- 본문이 있을 때 홈 이동·로그아웃을 확인하며, 탭 종료 경고는 보조 수단으로만 사용한다. 모바일에서는 종료 경고가 보장되지 않는다.
- 게시 성공이 확인됐을 때만 해당 초안을 제거한다.

**완료 기준:** 새로고침 후 초안 복원, 계정 간 격리, 게시 실패 후 본문 유지, 게시 성공 후 초안 제거를 확인한다.

### 3.2 게시 대기·오류·중복 처리 — P1

**관찰:** `addDoc()` 응답을 기다리는 동안 입력창과 로그아웃이 비활성화된다. Firestore는 연결이 끊기면 쓰기 완료가 바로 실패하지 않고 대기할 수 있다. 목록에는 확정 전 로컬 쓰기가 보일 수도 있다.

**제안:**

- `전송 중`, `연결 대기`, `게시 완료`, `실패`를 구분한다. 서버 확인 전 게시물에는 `전송 중` 표시를 붙인다.
- 지연이 길어지면 본문을 보호하면서 상태와 다음 행동을 안내한다.
- 단순히 화면 대기 시간을 초과했다고 실패로 판정하거나 새 문서로 재전송하지 않는다. 화면의 타임아웃은 기존 Firebase 쓰기를 취소하지 않는다.
- 게시 시도별 문서 ID를 한 번 생성·보관해 서버 저장 여부를 확인한 후 재시도한다. 이미 저장된 글은 성공으로 처리하는 등 중복 방지 흐름을 설계한다.
- 오류 메시지는 사용자의 행동 중심으로 쓰고, 기술적 설정 오류는 운영자가 확인할 수 있도록 분리한다.

**완료 기준:** 오프라인 게시 → 재연결, 느린 응답, 권한 거부, 연속 클릭에서 본문이 유실되지 않고 같은 게시 시도가 중복 문서를 만들지 않는다.

### 3.3 비밀번호 재설정과 가입 상태 복구 — P1

**관찰:** 로그인 폼에 비밀번호 재설정 경로가 없다. 가입 후 닉네임 저장 실패는 `window.alert()`로 안내하며 사용자가 다시 저장할 경로가 없다.

**제안:** Firebase `sendPasswordResetEmail()`을 사용한 재설정 화면을 추가한다. 계정 존재 여부를 단정하지 않는 발송 안내, 재전송 대기, 실패 상태를 제공한다. 가입 완료와 닉네임 저장 완료도 구분하고, 닉네임 실패는 화면 안에서 다시 시도하도록 한다.

**완료 기준:** 실제 수신 가능한 테스트 메일로 재설정 후 로그인에 성공한다. 닉네임 저장 실패 시 계정을 다시 생성하도록 안내하지 않는다.

### 3.4 본인 글 삭제, 이후 수정 — 삭제 P1 / 수정 P2

**관찰:** 현재는 작성자의 수정·삭제도 규칙에서 모두 금지한다. 사용자는 오탈자나 잘못 올린 내용을 회수할 수 없다.

**제안:**

- 본인 글 메뉴에 삭제와 확인 절차를 먼저 추가하고, 진행·실패 상태를 표시한다.
- UID가 작성자와 일치하는 경우에만 삭제를 허용한다. 버튼 숨김과 별개로 Firestore 규칙을 바꾼다.
- 수정 추가 시 변경 가능한 필드를 `body`, `updatedAt` 등으로 제한하고 `authorId`, `createdAt` 변경을 금지한다. 수정 시에도 본문 검증을 적용한다.
- 수정 시각을 표시하고, 편집 취소 시 기존 글과 작성 중 편집본을 구분한다.

**완료 기준:** 본인은 삭제·수정할 수 있고 다른 계정과 비로그인 사용자는 SDK 직접 호출로도 수행할 수 없다. 작성자·원래 게시 시각 변조가 거절된다. 규칙 테스트의 기존 ‘모두 금지’ 기대값도 새 정책에 맞춰 갱신한다.

## 4. 화면과 탐색 개선

### 4.1 읽기와 조작의 접근성 — P1

**관찰:** CSS에서 날짜는 10px, 보조 문구는 10~11px이고 일부 모바일 버튼은 10px이다. 연한 보조 글씨와 작은 ‘내 글’ 배지도 사용한다. 첨부 화면에서도 날짜와 안내 문구가 상대적으로 약하게 보인다. 대비 미달 여부는 측정이 필요하다.

**제안:** 본문·입력은 15~16px, 주요 보조 문구는 12~14px를 출발점으로 조정한다. 일반 텍스트 대비 4.5:1을 확인하고, 작은 버튼은 터치 영역을 여유 있게 확보한다. 로그인 폼을 열면 첫 필드로 초점을 보내고 닫으면 열었던 버튼으로 돌려준다. 오류를 필드와 연결하고 성공 안내는 스크린리더에서도 읽히게 유지한다.

**완료 기준:** 200% 확대와 360px 화면에서 주요 조작이 가능하고, Tab·Enter만으로 로그인과 게시를 수행한다. 날짜·보조 문구의 대비를 도구로 측정하고 자동 검사와 수동 키보드 검사를 함께 통과한다.

### 4.2 로그인 후 화면을 기록 중심으로 — P2

**관찰:** 첨부 화면에서 큰 소개 영역과 왼쪽 안내 카드가 작성·목록보다 넓은 영역을 차지한다. 처음 방문한 사용자에게는 유용하지만 반복 방문 때도 같은 공간을 사용한다.

**제안:** 비로그인 화면의 소개는 유지하고, 로그인 후에는 소개를 한 줄로 줄이거나 접는다. 왼쪽 카드는 ‘모든 글 / 내 글’ 탐색으로 전환한다. 큰 작성창은 집중 작성에 유지하되 로그인 후 첫 게시물이 더 일찍 보이도록 여백을 조정한다. 한국어 서비스에서 영어 장식 문구의 필요성도 정리한다.

**완료 기준:** 데스크톱과 모바일의 정해진 화면 높이에서 작성 시작과 첫 글 확인이 쉬워지는지 전후 화면으로 비교한다. 차분한 색과 카드 디자인은 유지한다.

### 4.3 이전 글 더 보기와 내 글 — P2

**관찰:** 쿼리가 최신 50개로 고정되어 이전 글을 읽을 방법이 없다. 제목 옆 `posts.length`도 전체 글 수가 아닌 현재 불러온 글 수다.

**제안:**

- 우선 숫자를 ‘불러온 글 N개’로 명시한다. 총 개수가 꼭 필요할 때 별도 집계 방식을 설계한다.
- 커서 기반 ‘더 보기’를 제공한다. 최신 구간의 실시간 구독과 과거 구간 조회를 분리한다.
- 새 글 유입·삭제·동일 시각 데이터에서 문서 ID 기준으로 중복을 제거하고 페이지 경계를 검증한다.
- ‘내 글’에는 `authorId` 필터를 사용하고, 정렬과 결합하는 쿼리에 필요한 복합 인덱스를 저장소에서 관리한다.

**완료 기준:** 에뮬레이터에 100개 이상을 준비해 전체 탐색, 중복·누락 방지, 새 글 유입 시 스크롤 유지, 다른 계정의 내 글 분리를 확인한다.

### 4.4 상세 주소와 공유 — P2

게시물별 ‘링크 복사’와 상세 보기를 추가한다. GitHub Pages는 임의 하위 경로 새로고침을 자동 처리하지 않으므로 초기에는 `/Postpost/#/posts/{id}` 같은 해시 경로가 간단하다. 링크 직접 접근, 삭제된 글, 권한 오류를 처리한다.

일반적인 소셜 미리보기 수집기는 JavaScript를 실행하지 않을 수 있다. 글별 OG 미리보기가 필요해지면 별도 HTML 생성·호스팅 방식을 검토하고, 클라이언트 메타 태그 변경만으로 해결된다고 가정하지 않는다.

### 4.5 닉네임·계정 관리 — P2

닉네임 변경, 비밀번호 변경, 탈퇴 진입점을 추가한다. 현재 글에는 작성 당시 `authorName`을 복사하므로 닉네임을 바꿔도 과거 글에는 반영되지 않는다. 초기에는 ‘과거 글은 당시 이름 유지’가 단순하다. 전체 반영이 필요하면 UID별 프로필 조회 구조와 읽기 비용을 함께 설계한다.

닉네임은 인증된 신원이나 고유 이름이 아니라는 점을 유지한다. 현재 생성 규칙은 닉네임을 인증 프로필과 대조하지 않는다. 신뢰할 수 있는 프로필 표시가 필요하면 프로필 변경 권한과 글 작성 시 일치 검증을 추가한다.

탈퇴 시 Auth 계정 삭제만으로 Firestore 글이 삭제되지는 않는다. ‘글 삭제 후 탈퇴’ 또는 ‘동의 후 익명화·유지’를 먼저 결정하고, 재인증 및 부분 실패 복구를 포함한다.

## 5. 운영과 유지보수

### 5.1 규칙·브라우저 테스트를 배포 검증에 포함 — P2

현재 Actions는 입력 검증 테스트와 빌드를 실행하지만, 저장소에 있는 `test:rules`는 실행하지 않는다. 이전 작업에서는 에뮬레이터 다운로드가 차단돼 규칙 테스트를 끝내지 못했으며 이번 문서 작성에서는 재실행하지 않았다.

- Java 21과 Firestore 에뮬레이터를 준비하는 CI 검증 작업을 추가하고, 규칙 테스트 통과를 배포 조건으로 삼는다.
- 테스트는 데모 프로젝트를 사용한다. 비로그인 생성, 작성자 위조, 공백·초과 본문, 추가 필드와 수정·삭제 권한을 검사한다.
- Auth·Firestore 에뮬레이터를 연결할 개발 전용 설정을 추가해 로그인 → 게시 → 새로고침 → 로그아웃 흐름을 자동화한다. 운영 빌드에서는 에뮬레이터 연결을 허용하지 않는다.
- 현재의 Pages 경로·홈 링크 검사도 회귀 테스트로 보존한다. 운영 사이트에는 임의 테스트 계정이나 게시물을 자동 생성하지 않는다.

### 5.2 공개 이용에 맞는 관리·사용량 관찰 — P2

소수 사용자 단계에는 운영자가 콘솔로 대응할 수 있다. 공개 이용을 늘리기 전에는 신고 접수, 운영자 숨김·삭제, 이용 안내와 문의 경로를 마련한다. 관리자 권한은 서버에서 부여하고 클라이언트가 스스로 설정할 수 없도록 한다.

현재 `allow read: if true`이므로 글은 공개 데이터다. UI의 `limit(50)`은 직접 SDK를 사용하는 접근까지 제한하지 않는다. 필요하면 단건 읽기와 목록 읽기를 구분하고 목록 쿼리의 최대 개수를 규칙으로 제한하되, 이것만으로 반복 요청 제한이 되는 것은 아니다.

App Check는 비정상 클라이언트 접근을 줄이는 보조 장치로 검토한다. 사용자별 게시 빈도 제한이 필요하면 신뢰할 수 있는 서버 측 처리와 우회 불가능한 쓰기 규칙을 설계한다. 버튼 비활성화나 브라우저 타이머만으로 제한하지 않는다. 서버 기능 도입 시 요금제·유지 비용을 먼저 확인한다.

Firestore 읽기·쓰기 추세, 오류와 지연을 관찰하고 이용 규모에 맞는 알림을 설정한다. 예산 알림은 자동 비용 차단 장치가 아니다. 오류 수집에는 글 본문·비밀번호·토큰을 넣지 않는다.

### 5.3 코드 구조·성능·배포 관리 — P2

- `App.tsx`의 계정 폼, 작성창, 목록, 카드와 Firebase 구독 로직을 기능별로 분리한다. 새 기능을 추가하는 시점에 필요한 만큼 진행한다.
- 한 줄로 압축된 `style.css`를 읽기 쉬운 규칙과 공통 색·간격 값으로 정리해 수정 부담을 줄인다.
- Firestore 응답을 단순 타입 단언으로 사용하는 부분에 런타임 검증을 추가한다. 콘솔·향후 마이그레이션으로 생긴 잘못된 날짜나 필드가 전체 목록을 중단시키지 않도록 한다.
- 이전 빌드의 번들 크기 경고는 모바일에서 측정 후 대응한다. Firebase 모듈과 계정 UI의 지연 로딩을 검토하고, 측정 없이 분할 자체를 목표로 삼지 않는다.
- 배포 성공과 실제 서비스 확인을 구분해 기록한다. Node 런타임 경고가 있는 Actions는 공식 호환 버전을 확인해 갱신한다.
- Firestore 규칙은 Pages와 별도로 게시된다. 규칙 변경의 적용 순서와 이전 프런트엔드 호환성을 확인하고, 검증된 이전 커밋 재배포 절차를 문서화한다.

## 7. 권장 작업 순서와 출시 확인

1. **작성 안정성:** 초안 보호, 게시 대기 상태, 재시도·중복 처리. 네트워크 장애에서도 글을 잃지 않는지 확인한다.
2. **사용자 관리:** 비밀번호 재설정, 본인 글 삭제, 작은 글씨·초점 개선. 수정·삭제 권한 테스트를 함께 보강한다.
3. **반복 방문:** 이전 글 더 보기, 내 글, 소개 영역 축소, 닉네임 관리. 50개 이상의 글과 두 계정으로 검증한다.
4. **공유와 공개 운영:** 상세 링크, 신고·관리, 사용량 관찰. Pages 직접 접근·새로고침과 공개 데이터 정책을 확인한다.
5. **선택적 확장:** 실제 피드백을 보고 북마크·공감·댓글·포스터 중 한 묶음씩 추가한다.

각 출시에서는 규칙 테스트 → 입력·브라우저 테스트 → 빌드 → 배포 → 실제 사이트 확인 순으로 검증한다. 운영 환경에서 데이터를 생성하는 검증은 전용 테스트 계정과 삭제 가능한 글로 수행하고 정리한다. 이번 문서는 작업 후보를 정리한 것이며 구현·push·배포 승인을 대신하지 않는다.

## 9. 이번 beta 구현 결과와 검증

요청한 About 분리, 반응, 리포스트, 기본 16pt·최소 15pt 타이포그래피, 태그·검색을 구현했다. 필수 사용 흐름으로 초안 복원·중복 방지용 게시 ID 보관·비밀번호 재설정·내 글·수정·삭제·공유 링크를 추가했다. 큰 작성창은 접어 두고, 초안이 있으면 펼쳐 피드 공간과 가독성을 함께 확보했다.

검증한 범위:

- 입력·검색 테스트 7개: 공백·글자 수 경계, 가입 조건, 한글 태그·대소문자 정규화·중복 제거·정확한 태그 검색.
- Firestore 에뮬레이터 테스트 11개: 기존 글 호환, 본인 편집·내용 삭제, 다른 계정의 조작 거부, 반응 변경·취소, 반응자 정보 접근 제한, 집계 위조 거부, 중복 방지 리포스트·재리포스트·삭제 원문 처리.
- 실제 Chromium에서 데모 두 계정을 이용한 게시·새로고침 초안 복원·반응 전환·작성자 전용 명단·리포스트·원문 창·검색·수정·삭제 흐름과 모바일 About·비밀번호 재설정 흐름을 검증한다. 두 통합 테스트가 모두 통과했다. 운영 계정이나 운영 글은 테스트에서 생성하지 않았다.
- 주요 텍스트·배경 9개 조합의 대비를 계산했으며 최소 5.30:1로 일반 텍스트 4.5:1 기준을 넘는다. 모바일 테스트는 표시된 글씨가 20px(15pt) 이상인지와 가로 넘침이 없는지 확인한다.
- TypeScript·프로덕션 빌드 및 Actions 정적 검사를 통과했다. Pages용 About 정적 HTML 생성과 자산 경로를 확인했다.

운영 적용 시 사용자가 할 작업:

1. 저장소의 최신 `firestore.rules` 전체를 Firebase 콘솔의 Firestore → 규칙에서 게시한다. 기존 생성·읽기도 허용해 기존 텍스트 앱과 호환된다. Pages push는 운영 규칙을 적용하지 않는다.
2. `beta`의 Actions에서 검증·빌드·배포 성공을 확인한다.
3. 운영 사이트에서는 테스트용 글로 반응·원문 창·수정·삭제를 확인한다. 다른 계정에 반응한 사람 버튼이 없는지 확인하고, 규칙 테스트로 SDK 직접 접근도 거절되는지 확인한다.

남은 범위·제약:

- 검색과 내 글 필터는 현재 불러온 글에 적용된다. 전체 DB 검색 서비스나 전역 총 개수는 제공하지 않는다.
- 삭제는 본문·태그를 제거하는 삭제 표시 방식이며 참조·반응 메타데이터는 남는다. 계정 탈퇴와 모든 연관 데이터의 영구 삭제는 후속 범위다.
- 초안은 탭 저장소에 보관되며 브라우저·기기 간 동기화되지 않는다. 오프라인에서는 새 게시를 안내 후 중단하고, 응답 지연 중에는 같은 ID를 유지한다.
- 댓글·이미지·신고·프로필 변경·탈퇴·전문 검색은 구현하지 않았다.
- Firebase SDK가 포함된 단일 번들 크기 경고는 남아 있다. 통합 테스트 통과와 별개로 향후 모바일 네트워크 성능 측정 후 분할을 검토한다.


## 10. 화면 및 프로필 개편 — 최신 요구사항

- 검색은 상단 돋보기 아이콘으로 열리는 팝업으로 이동했다. 모든 글·내 글 탭은 피드에서 항상 보이며 검색 팝업 안에서도 범위를 바꿀 수 있다. 현재 이름과 @핸들도 검색한다.
- 화면 메뉴를 ‘피드 / 소개’로 통일했다. 기존 `/Postpost/About/` 주소는 호환을 위해 유지하며 표시 문구는 한국어를 사용한다.
- PC는 로그인·새 글 쓰기를 왼쪽 사이드바에서 바로 수행한다. 모바일은 상단 프로필 아이콘에서 로그인·마이페이지로 이동하고 글쓰기는 별도 창에서 진행한다.
- 본문은 14pt, 핸들·날짜 등 부가 정보는 10~12pt로 조정했다. 큰 설명·검색 패널을 피드에서 제거하고 아이콘과 여백으로 정보 밀도를 조절했다. 프로필 이미지를 대신하던 원형은 제거했다.
- 게시물 하단은 좋아요·싫어요의 빈/찬 아이콘과 숫자, 리포스트 아이콘과 실제 개수, 오른쪽 더보기로 구성한다. 더보기에는 정보·링크 복사, 작성자에게는 반응한 사람·수정·삭제를 아이콘과 텍스트로 제공한다.
- 고유 핸들은 소문자 영문·숫자·밑줄 3~20자(영문자로 시작)이며, 최초 등록 후 최근 14일 동안 두 번까지 바꾼다. 동시 등록 중복과 변경 제한은 서버 규칙으로 검증한다. 바꾼 이전 핸들은 다시 사용 가능해진다.
- 마이페이지에서 이름, 핸들, 소개 1,000자, https SNS 링크 5개까지 추가·편집·제거한다. 공개 프로필과 작성자·반응자 표시는 현재 이름·핸들을 사용하고 UID를 직접 표시하지 않는다. UID는 내부 권한·참조용으로 유지한다.
- `profiles` 공개 데이터, `handles` 고유 예약, `profileLimits` 본인 전용 변경 이력을 분리한다. 계정이나 이력을 삭제해 제한을 초기화하는 요청은 거절한다.
- 기존 사용자는 마이페이지에서 프로필을 최초 등록한다. 게시물 일괄 마이그레이션은 필요 없다. 운영 DB에서는 새 `firestore.rules`를 다시 게시해야 프로필 기능을 사용할 수 있다.

검증에는 입력·프로필 검증, 핸들 동시 등록 및 14일 제한·초기화 우회 거부, PC 사이드 작성, 모바일 로그인과 프로필 편집, 반응자 공개 범위, 리포스트 개수·취소, 상단 검색 팝업, 한국어 메뉴, 본문 크기·대비·가로 넘침을 포함한다.

최종 확인 결과: 입력·검색·프로필 테스트 10개, Firestore 규칙 테스트 14개, 실제 Chromium 통합 시나리오 2개가 통과했다. TypeScript·프로덕션 빌드·Actions 정적 검사도 통과했다. 텍스트 색 조합 10개의 최소 대비는 4.86:1이었다. PC·모바일 화면 캡처를 검토했으며 마이페이지의 긴 소개는 편집 화면 위에서 세 줄 미리보기로 줄여 편집 폼에 빨리 접근하도록 했다. 큰 Firebase 번들의 크기 경고는 기존 후속 성능 작업으로 남는다.

## 11. 내비게이션·가입·인증·테마 개편 — 2026-11-06

인증 서버 부분은 12절의 외부 서버 없는 설계로 대체되었다.

최신 요구사항으로 10절의 PC 사이드 폼·검색 팝업을 대체한다.

- PC는 왼쪽 고정 레일에 상징 포스트 아이콘, 중앙 피드·탐색·게시물 추가·검색·마이페이지, 아래 더보기(설정·내 활동·소개·로그아웃)를 배치한다. 모바일은 같은 순서의 하단 다섯 메뉴를 고정한다.
- 프로필 제목은 ‘프로필’로 명시하고 왼쪽 뒤로 가기 버튼으로 직전 앱 화면으로 돌아간다. 직접 접근한 첫 화면에서는 피드를 대체 경로로 사용한다. 로그인도 같은 뒤로 가기 아이콘을 사용한다.
- 가입은 이메일·비밀번호 → 필수 핸들·닉네임 순서다. 이메일을 `autocomplete=username`, 비밀번호를 `new-password`로 지정하고 닉네임을 로그인 사용자명으로 지정하지 않는다. 두 번째 단계에서 이메일은 읽기 전용으로 표시하고 비밀번호는 같은 폼에 숨겨 유지한다. 비밀번호 관리자 자체의 저장·제안 UI는 사용자 브라우저에서 별도 확인한다.
- 이메일 로그인에 더해 핸들 로그인을 추가한다. 이메일은 공개 매핑에 저장하지 않는다. Functions가 비밀번호·계정 UID를 확인한 뒤에만 이메일을 반환하고 브라우저는 표준 Firebase Auth 로그인으로 세션을 만든다. 서버 로그·DB에 비밀번호나 토큰을 기록하지 않는다.
- 핸들 로그인 서버 운영 배포에는 Blaze와 `AUTH_WEB_API_KEY` 설정이 필요하다. Pages 배포는 Functions를 배포하지 않는다. 자세한 절차는 `functions/README.md`에 기록한다. 서버 미배포 상태에서도 이메일 로그인은 유지한다.
- 검색은 `#/search`에서 검색란을 확장하며, 탐색은 불러온 글의 반응순·해시태그를 제공한다. 내 활동은 최근 100개 개인 기록과 불러온 이전 글의 반응을 결합한다. 전체 DB 전문 검색·전체 활동 무제한 조회는 아니다.
- 개인 활동은 본인만 읽고 실제 반응·리포스트에 맞는 기록만 저장할 수 있다. 원문 수정·삭제와 반응 취소를 실시간 반영한다. 이전 버전의 활동 기록 없는 반응·리포스트 취소도 지원한다.
- 링크 복사 SVG 경로가 뷰박스를 넘지 않도록 수정하고 아이콘 영역을 잘라내지 않게 한다.
- 설정에 기기·라이트·다크 모드를 추가하고 선택을 저장한다. 초기 HTML에서도 선택을 적용해 새로고침 시 밝은 화면이 깜빡이는 현상을 줄인다. 모션 감소 설정도 존중한다.
- 규칙에는 개인 활동 및 서버 전용 요청 제한 기록이 추가된다. 운영에서는 최신 규칙과 Functions를 별도 배포해야 한다.

검증 결과: 입력·프로필 테스트 10개, 로그인 서버 테스트 3개, Firestore 규칙 테스트 17개, 실제 Chromium의 PC·모바일 통합 시나리오 2개가 통과했다. TypeScript·빌드·Actions 정적 검사와 정적 소개 진입 파일도 확인했다. 대표 텍스트 대비의 최소값은 라이트 4.86:1, 다크 6.46:1이다. 통합 시나리오에는 실제 Functions 에뮬레이터의 핸들 로그인, 틀린 비밀번호에서 이메일 비공개, 활동 화면의 원문 삭제 반영, 뒤로 가기, 두 단계 가입, 테마 재시작 유지, 링크 SVG 경계 확인이 포함된다. 운영 Functions 배포·IAM·브라우저별 비밀번호 저장 UI는 사용자가 배포 후 확인해야 한다. 기존 단일 Firebase 번들 크기 경고는 후속 성능 작업으로 남는다.


## 12. 외부 서버 없는 인증 재설계 — 2026-11-06

사용자 선택에 따라 Firebase Functions와 다른 무료 API 서버 모두 추가하지 않는다. [인증 설계](AUTH_DESIGN.md)에 제공 범위와 이행 방식을 정리했다.

- Firebase Functions 서버·패키지·SDK 호출·CI·에뮬레이터 설정을 제거한다.
- 로그인은 이메일로 명시하고 Firebase Auth에 직접 요청한다. 기존 이메일 비밀번호 재설정과 계정을 유지한다.
- 핸들은 계속 필수 프로필 식별자이며, 공개 주소·작성자 표시·검색과 고유성·14일 변경 제한은 유지한다.
- 공개 이메일 매핑, 가상 이메일로 기존 계정 변경, 브라우저 전용 이메일 매핑으로 전역 핸들 로그인을 흉내 내는 방식은 사용하지 않는다.
- 이번 설계는 전역 핸들 로그인은 제공하지 않는다. 기능이 유료이기 때문이 아니라 현재 Firebase Auth 이메일 계정과 이메일 비공개·외부 서버 없음이라는 조건을 보존하기 위한 명시적인 범위 결정이다.
- 새 인증 서버·키·Blaze 설정이 필요 없다. 기존 운영 Functions가 있다면 삭제는 별도 운영 작업이며 이번 변경에서는 자동 삭제하지 않는다.

## 13. 다크모드와 아이콘 내비게이션 수정 — 2026-11-06

다크모드의 페이지·카드·입력창·내비게이션 배경은 `#000000`, 본문은 `#FFFFFF`로 변경했다. 보조 정보는 중립 회색으로 표시하고 초록색은 테두리·포커스·내비게이션 아이콘에만 제한한다. 버튼·선택·호버 배경도 녹색 대신 검정·회색을 사용하며 초기 테마와 브라우저 테마 색도 검정으로 맞춘다.

PC 레일과 모바일 하단의 다섯 메뉴는 표시 텍스트 없이 아이콘만 사용한다. 더보기 진입점도 아이콘으로 바꾸되, 열린 작업 메뉴의 항목 이름은 유지한다. `aria-label`, `aria-current`, 툴팁으로 접근성과 선택 상태를 유지한다. PC 레일 폭을 줄여 불필요한 텍스트 공간을 제거한다.

Chromium의 PC·모바일 통합 시나리오 2개가 통과했다. 메뉴의 텍스트가 비어 있는지, 페이지·카드·하단 바의 실제 계산 색이 검정인지, 본문이 흰색인지 확인하고 화면 캡처를 검토했다.


## 14. 글을 덧붙이는 리포스트와 댓글

- 리포스트 아이콘은 작성 창을 연다. 선택적으로 최대 2,000자의 글과 해시태그를 덧붙이고 원문 작성자·본문 일부를 미리 본다. 글 없이 공유하는 기존 방식도 지원한다.
- 계정·원문당 활성 리포스트 하나를 유지한다. 다시 누르면 덧붙인 글 수정·리포스트 취소가 가능하며, 본인 리포스트의 더보기에서도 수정·삭제할 수 있다. 내 활동에는 공유한 리포스트 자체를 표시한다.
- 원문을 복사해 저장하지 않는다. 원문이 삭제되면 참조 내용은 숨기고 덧붙인 글과 리포스트 자체의 댓글은 유지한다. 리포스트의 재리포스트는 지원하지 않는다.
- 일반 글과 리포스트에 각각 댓글 아이콘·개수를 표시하고 게시물 창 안에서 댓글을 읽고 작성한다. 댓글은 별도 하위 컬렉션에 보관하며 두 게시물의 댓글을 섞지 않는다.
- 댓글은 로그인 후 공백이 아닌 최대 1,000자로 작성한다. 작성자는 더보기에서 자기 댓글만 수정·삭제할 수 있다. 현재 핸들·이름을 표시하고 UID를 화면에 표시하지 않는다.
- 최신 50개부터 불러와 시간순으로 표시하고 이전 댓글을 추가로 불러온다. 이 탭의 계정·게시물별 초안을 보존하고 등록 재시도 시 같은 문서 참조로 중복 작성을 막는다.
- 댓글 생성·삭제와 공개 개수를 같은 트랜잭션에서 처리한다. 카운터는 원자적으로 증가·감소하며 보안 규칙이 실제 댓글 변경과 작성자 권한을 검증한다. 임의 개수 변경·작성자 위조·타인 댓글 변경·단독 댓글 생성은 거절한다.
- 댓글 삭제는 본문을 비우는 방식이다. 부모 게시물 삭제 후 댓글 조회·작성·수정도 규칙에서 거절한다. 보존된 삭제 표시는 완전한 개인정보 삭제 기능이 아니다.
- 답글·알림·댓글 검색·신고·차단은 후속 범위다. 검정 배경·흰 본문과 아이콘 내비게이션을 유지한다.

운영 적용에는 최신 `firestore.rules` 게시가 필요하다. 새 인증 서버·키·요금제 전환·복합 인덱스는 추가하지 않는다. 검증 범위는 리포스트의 선택적 본문·수정·복원·원문 고정, 댓글 동시 작성·정확한 개수·길이·작성자 권한·삭제, 원문 삭제 후 리포스트 댓글의 독립성, PC·모바일 실제 브라우저 흐름을 포함한다.

검증 결과: 입력 검증 테스트와 TypeScript·프로덕션 빌드, Firestore 규칙 테스트 22개, Chromium 통합 시나리오 3개, Actions 정적 검사가 통과했다. 모바일 검정 테마 화면과 가로 넘침도 확인했다. 운영 DB 규칙 게시는 별도이며 기존 Firebase 번들 크기 경고는 성능 개선 후보로 유지한다.
