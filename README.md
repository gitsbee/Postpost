# Postpost

Firebase 기반의 가벼운 텍스트 게시판입니다. React + TypeScript + Vite를 사용합니다.

- 이메일·비밀번호 → 핸들·닉네임의 두 단계 회원가입, 이메일 로그인, 비밀번호 재설정
- PC 왼쪽 내비게이션·모바일 하단 5개 메뉴, 프로필·로그인 뒤로 가기, 라이트·다크·기기 모드
- 텍스트 작성·수정·삭제, 이 탭에서 UID별 초안 복원
- 좋아요·싫어요 선택·전환·취소, 작성자만 반응자 목록 확인
- 아이콘 반응·숫자, 리포스트·취소와 실시간 개수, 더보기 메뉴, 원문 창·링크 복사
- 자연스럽게 확장되는 검색 화면에서 본문·작성자·@핸들·#태그 검색, 모든 글·내 글 탭
- 탐색의 반응순 글·주요 태그와 본인만 볼 수 있는 내 활동(좋아요·싫어요·리포스트)
- 최신 50개부터 이전 글 더 불러오기, 실시간 갱신
- 고유 핸들, 이름·1,000자 소개·SNS 링크 편집, 공개 프로필·마이페이지

이번 구현과 후속 후보는 [개선 계획](docs/IMPROVEMENT_PLAN.md)을 참고하세요. 댓글·이미지·신고·계정 탈퇴는 후속 범위입니다.

## 로컬 실행

Node.js 22.12 이상이 필요합니다. 현재 클라우드에서는 Node.js 24로 검증했습니다.

```sh
npm ci
cp .env.example .env.local
# .env.local의 네 항목을 채운 뒤 실행
npm run dev
```

이미 `.env.local`이 있으면 복사하지 말고 기존 파일을 편집하세요. 환경 변수를 수정하면 개발 서버를 다시 시작하세요. 키가 없으면 안내 화면을 보여주며 Firebase 요청을 보내지 않습니다.

```sh
npm test       # 입력 검증 테스트
npm run build # TypeScript 검사 + 프로덕션 번들
npm run preview
```

Firestore 보안 규칙 테스트는 Java 21 이상과 에뮬레이터 다운로드 권한이 필요합니다. 실제 Firebase 키나 프로젝트는 필요하지 않습니다.

```sh
npm run test:rules
```

현재 클라우드에서는 에뮬레이터 다운로드가 허용되어 규칙 테스트를 실행할 수 있습니다. 브라우저 통합 검증은 운영 프로젝트 대신 데모 Auth·Firestore를 사용합니다.

```sh
npx playwright install chromium
npm run test:e2e
# 시스템 Chromium을 사용할 때:
# PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium npm run test:e2e
```

브라우저 테스트 설정은 로컬 Vite 서버에 데모 설정을 주입합니다. `VITE_FIREBASE_USE_EMULATORS=true`는 개발 모드·로컬 호스트·`demo-postpost` 프로젝트에서만 동작하며 운영 빌드에는 적용되지 않습니다.

## Firebase 프로젝트 연결

1. [Firebase Console](https://console.firebase.google.com/)에서 프로젝트를 만들고 **프로젝트 설정 → 일반 → 내 앱 → 웹 앱**을 등록합니다. Analytics는 필요하지 않습니다.
2. 웹 앱의 `firebaseConfig`에서 아래 값을 `.env.local`에 입력합니다.

   | 환경 변수 | firebaseConfig 필드 |
   | --- | --- |
   | `VITE_FIREBASE_API_KEY` | `apiKey` |
   | `VITE_FIREBASE_AUTH_DOMAIN` | `authDomain` |
   | `VITE_FIREBASE_PROJECT_ID` | `projectId` |
   | `VITE_FIREBASE_APP_ID` | `appId` |

3. **Authentication → Sign-in method**에서 **이메일/비밀번호**를 활성화합니다. 이메일 링크 로그인은 사용하지 않습니다. 가입 폼은 최소 8자를 요구합니다. 콘솔에서 더 강한 비밀번호 정책을 적용하면 해당 조건도 충족해야 합니다.
4. **Authentication → Settings → Authorized domains**에 실제 서비스 도메인을 등록합니다. 로컬 개발에는 `localhost`도 등록하세요. 최근 생성된 프로젝트에서는 자동 등록되지 않을 수 있습니다.
5. **Firestore Database**를 생성합니다. 보안 규칙을 아래 `firestore.rules` 내용으로 배포하기 전까지 서비스를 공개하지 마세요. `posts` 컬렉션은 첫 게시 시 생성됩니다. 별도 복합 인덱스는 필요하지 않습니다.

이 네 값은 브라우저에서 사용하는 **공개 웹 앱 설정**이며 빌드 결과에 포함됩니다. 서비스 계정 JSON, Admin SDK 개인 키, 비밀번호를 `VITE_` 변수에 넣지 마세요. `.env.local`은 Git에서 제외됩니다. 웹 API 키는 해당 프로젝트의 웹 앱 설정 값을 사용하세요. Firestore 접근 권한은 보안 규칙으로 제어합니다.

## 보안 규칙과 데이터

`posts/{id}`에 `body`, `authorId`, `authorName`, `createdAt` 및 `kind`, `originalId`, `tags`, `deleted`, 선택적 `updatedAt`을 저장합니다. 기존 글에 새 필드가 없어도 읽을 수 있으며 별도 일괄 마이그레이션은 필요하지 않습니다. 본문은 HTML로 해석하지 않고 일반 텍스트로 표시하며 이메일은 게시 데이터에 저장하지 않습니다.

- 읽기: 전체 공개. 작성·수정·삭제는 로그인과 작성자 UID로 검증합니다.
- 일반 글: 공백만 있는 본문 금지, 최대 2,000자, 닉네임 1~30자. 원 게시 시각·작성자 변경 금지.
- 삭제: 본문과 태그를 비우고 삭제 상태로 전환합니다. 참조와 권한 일관성을 위해 문서 ID·작성자·시각·반응 데이터는 남습니다. 모든 개인정보의 완전 삭제나 계정 탈퇴 기능은 아닙니다.
- 리포스트: `repost_{uid}_{originalId}` ID로 중복을 막으며 원문을 복사하지 않습니다. 원문이 삭제되면 원문 창에 내용이 표시되지 않습니다. 리포스트 아이콘은 등록·취소를 전환합니다. 활성 리포스트 개수는 원문 참조 쿼리로 집계하므로 기존 데이터도 반영합니다.
- 반응: `posts/{id}/reactions/{uid}`에 종류와 반응 당시 표시명을 보관합니다. 본인은 자기 반응을 단건 조회할 수 있고, 전체 목록은 글 작성자만 조회합니다. 제3자의 단건·목록 조회는 규칙에서 거절합니다. 화면의 반응자 목록에는 현재 프로필의 이름·핸들을 보여 주며 계정 ID를 표시하지 않습니다. 프로필이 없는 기존 사용자는 핸들 미설정으로 표시됩니다.
- 합계: `posts/{id}/stats/reactions`는 공개입니다. 반응 변경과 카운터를 같은 트랜잭션으로 갱신하고 규칙에서 차이를 검증하여 임의 집계 변경을 거절합니다.

해시태그는 공백으로 구분된 `#태그`를 최대 10개 인식합니다. 한글·영문·숫자·밑줄을 지원하며 태그당 최대 30자입니다. 검색은 현재 불러온 글 안에서 수행되며 전체 DB 전문 검색은 아닙니다. `#태그`와 `@핸들`은 정확히 일치해야 하고 여러 검색어는 모두 일치해야 합니다. 리포스트의 검색 대상은 리포스트 작성자이며 원문 내용은 원 게시물에서 검색합니다. ‘더 불러오기’는 구독 범위를 50개씩 넓히므로 데이터가 늘면 읽기 사용량도 늘어납니다.

## 프로필과 고유 핸들

- `profiles/{uid}`: 이름, 핸들, 소개(최대 1,000자), SNS 링크(https:// 최대 5개), 생성·수정 시각. 공개 프로필이며 문서 단건만 조회할 수 있습니다.
- `handles/{handle}`: 고유 핸들의 내부 소유자 매핑. 대소문자 차이로 중복 등록하지 않으며 영문자로 시작하는 소문자·숫자·밑줄 3~20자를 사용합니다.
- `profileLimits/{uid}`: 최근 두 번의 핸들 변경 시각. 본인만 읽을 수 있습니다. 최초 등록은 변경 횟수에 포함되지 않고 이후 최근 14일 동안 두 번까지 변경할 수 있습니다.
- 핸들 예약·이전 예약 해제·프로필·변경 시각을 하나의 트랜잭션으로 저장합니다. DB 규칙이 고유성, 횟수, 서버 시각과 소유권을 검증하며 삭제·재등록으로 횟수를 초기화할 수 없습니다.
- 이름·소개·SNS 링크는 핸들 변경 횟수와 무관하게 편집할 수 있습니다. 수정된 프로필은 이전 게시물과 반응자 표시에도 반영됩니다. 검색도 현재 이름·핸들을 사용합니다.
- 기존 계정은 마이페이지에서 프로필을 한 번 등록해야 새 글과 반응을 사용할 수 있습니다. 프로필 이미지는 사용하지 않습니다. 기존 글 자체는 계속 읽을 수 있습니다.
- 핸들을 바꾸면 이전 주소의 소유권은 해제됩니다. 이전 핸들이 다른 사용자에게 등록될 수 있으므로 공유한 프로필 주소도 갱신하세요.

UID는 인증·권한 확인과 내부 DB 참조에 계속 사용됩니다. 이를 비밀 값처럼 취급하거나 DB에서 제거하는 기능은 아니며, 화면의 사람 표시와 공개 프로필 주소는 핸들을 사용합니다. 컬렉션은 최초 프로필 저장 시 자동 생성되므로 수동으로 만들 필요가 없습니다.

## 외부 서버 없는 인증

Firebase Functions와 별도 API 서버를 사용하지 않습니다. 기존 Firebase Authentication의 이메일·비밀번호 로그인과 비밀번호 재설정을 그대로 사용합니다. 로그인 화면에는 이메일만 입력하도록 명시하며, 핸들은 프로필 주소·작성자 표시·검색용으로 유지합니다. 서버 키나 Blaze 가입은 필요하지 않습니다. [인증 설계](docs/AUTH_DESIGN.md)에 범위와 선택 이유를 기록했습니다.

회원가입 1단계의 이메일은 `name=username`, `autocomplete=username`이고 비밀번호는 `autocomplete=new-password`입니다. 2단계에서 핸들과 닉네임을 필수 입력합니다. 두 번째 단계에서도 이메일을 읽기 전용으로 표시하고 비밀번호를 같은 폼에 숨겨 유지하며 닉네임을 로그인 사용자명으로 지정하지 않습니다. 브라우저별 비밀번호 저장 동작은 실제 사용자 브라우저에서도 확인하세요. 인증 계정 생성 후 네트워크·핸들 중복으로 프로필 저장이 실패하면 계정을 다시 생성하지 않고 프로필 단계에서 재시도합니다.

`users/{uid}/activity/{id}`에는 본인의 반응·리포스트 참조와 갱신 시각을 저장합니다. 다른 사용자는 읽거나 쓸 수 없고, 실제 반응과 맞지 않는 활동 기록은 규칙에서 거절합니다. 최근 100개 활동을 불러오며 기존 버전의 반응은 현재 불러온 게시물에서 추가 확인합니다. 원문이 삭제된 활동은 표시하지 않습니다. 탐색도 불러온 글 범위에서 반응순과 해시태그를 제공합니다.

다크모드는 설정에서 선택하고 브라우저 저장소에 유지합니다. 기기 모드는 OS 테마 변경에 따라 전환합니다. 검색은 팝업이 아닌 독립 경로 `#/search`에서 검색란을 펼치며, 탐색 `#/explore`, 내 활동 `#/activity`, 설정 `#/settings`도 Pages에서 직접 접근할 수 있습니다.

## GitHub Pages 배포

배포 주소는 `https://gitsbee.github.io/Postpost/`입니다. Vite의 `base`와 홈 링크는 `/Postpost/` 경로를 사용합니다. 로컬 개발·미리보기도 서버 주소 뒤에 `/Postpost/`를 붙여 접속하세요. 화면 메뉴의 ‘소개’는 호환 경로인 `/Postpost/About/`이며 빌드 때 정적 진입 HTML을 생성하므로 Pages에서 직접 열기·새로고침이 가능합니다. 글 상세 링크는 `#/posts/{id}`, 공개 프로필은 `#/profile/{handle}`, 마이페이지는 `#/me`를 사용합니다.

1. 저장소 **Settings → Pages → Build and deployment → Source**를 **GitHub Actions**로 설정합니다.
2. **Settings → Secrets and variables → Actions**에서 위 네 가지 `VITE_FIREBASE_*` 값을 같은 이름으로 등록합니다. Repository secrets와 variables를 모두 지원하고, 같은 이름이면 secret을 우선합니다. 클라우드 환경 설정 값은 Actions로 자동 전달되지 않습니다.
3. Firebase Authentication의 **Authorized domains**에 `gitsbee.github.io`를 등록합니다. Firebase의 `authDomain` 값은 웹 앱 설정의 원래 값을 유지합니다.
4. `github-pages` 환경에 배포 브랜치 제한이 있다면 `beta`를 허용합니다.
5. 변경 사항을 `beta`에 push하면 `.github/workflows/deploy-pages.yml`이 설치 → 테스트 → 빌드 → Pages 배포를 수행합니다. Actions에서 수동 실행할 때도 `beta`를 선택해야 합니다. 다른 브랜치에서는 배포 작업을 건너뜁니다. 워크플로가 기본 브랜치에도 있어야 GitHub UI의 수동 실행 버튼이 표시될 수 있습니다.

워크플로는 데모 에뮬레이터의 규칙·브라우저 검증 후 Node.js 24에서 `npm ci`, `npm test`, 환경 변수 존재 검사, `npm run build`를 실행하고 `dist`만 Pages 아티팩트로 업로드합니다. 필수 변수가 비어 있으면 값은 출력하지 않고 빌드를 중단합니다. Pages 배포 권한은 배포 작업에만 부여합니다. Vite는 **빌드 시** 환경 변수를 번들에 반영하므로 값을 변경한 뒤에는 다시 빌드·배포해야 합니다.

## Firestore 보안 규칙 게시

**이번 버전 적용 시 아래 새 규칙을 Firebase 콘솔에 반드시 게시하세요.** 기존 프로필·핸들·개인 활동 권한을 포함한 규칙을 사용합니다. 이번 인증 재설계에서는 권한을 바꾸지 않습니다. 이전 버전 규칙만 적용되어 있으면 반응·리포스트와 함께 활동을 기록하는 작업이 거절될 수 있습니다. 새 규칙을 먼저 게시하세요. 기존 생성·읽기를 지원하므로 새 규칙을 먼저 게시해도 기존 텍스트 앱과 호환됩니다. GitHub Pages 워크플로는 규칙을 검증하지만 Firestore 규칙을 운영 DB에 배포하지 않습니다. Firebase 콘솔의 Rules 편집기에서 `firestore.rules`를 직접 게시하거나 본인 환경에서 다음 명령을 사용하세요. `YOUR_PROJECT_ID`는 실제 프로젝트 ID로 바꿉니다.

```sh
npx firebase-tools login
npx firebase-tools deploy --only firestore:rules --project YOUR_PROJECT_ID
```

## 연결 후 기능 확인

Actions의 빌드·배포 성공 후 Pages 주소에서 화면과 CSS가 표시되는지, 로고 클릭과 새로고침 후에도 `/Postpost/`에 머무는지 확인하세요. 실제 Firebase 프로젝트 연결 및 규칙 배포 후 다음을 확인하세요. 키가 없는 상태의 빌드와 입력 검증 테스트만으로 Firebase 연동 성공을 판단할 수 없습니다.

1. 이메일·비밀번호를 먼저 입력하고 다음 단계에서 핸들·닉네임을 등록한 뒤 프로필이 표시되는지 확인합니다.
2. 글을 게시하고 새로고침 후에도 로그인 상태와 글이 유지되는지 확인합니다.
3. 로그아웃한 상태에서 글 목록은 보이고 글 작성은 로그인으로 안내되는지 확인합니다.
4. 다른 브라우저에서 로그인해 글을 추가하고 첫 브라우저 목록에 실시간 반영되는지 확인합니다.
5. 다른 계정으로 좋아요 → 싫어요 → 취소를 수행하고, 작성자에게만 반응자 목록이 보이는지 확인합니다.
6. 리포스트에서 원문 창을 열고, 원문 삭제 후 내용이 숨겨지는지 확인합니다.
7. 본인 수정·삭제는 성공하고 다른 계정의 수정·삭제는 거절되는지 확인합니다.
8. 확장형 검색, 모든 글·내 글, 탐색·활동·소개 직접 접근을 확인합니다. PC 왼쪽·모바일 하단 메뉴의 순서와 프로필·로그인 뒤로 가기도 확인합니다.
9. 마이페이지에서 핸들·소개·SNS 링크를 저장하고 게시물·반응자 목록의 이름·핸들과 공개 프로필에 반영되는지 확인합니다.
10. `npm run test:rules`로 작성자 위조·반응자 정보 노출·카운터 변조 거절도 확인합니다.

운영 반영 시에는 이메일 로그인, 두 단계 가입, 내 활동, 다크모드 새로고침 유지 및 링크 아이콘 표시를 실제 사이트에서 확인하세요.

## 클라우드 작업

체크아웃 경로는 `/workspace/Postpost`입니다. 각 클라우드 작업은 격리되므로 기존 체크아웃을 사용하고, 명시적 요청 없이 별도 Git worktree를 만들지 마세요. 의존성은 `npm ci`, 개발 서버는 해당 경로에서 `npm run dev`로 실행합니다. Firebase 환경 변수는 환경 설정에 입력할 수도 있습니다. 프로세스는 새 작업에서 다시 실행해야 합니다.
